# 多语言（i18n）说明

这套方案的目标是：**在完全不改动业务逻辑的前提下**，让界面可以在英文与简体中文之间自由切换，
并且**以后同步 upstream 新版本时，不需要重新翻译一遍**。

- 英文是唯一的「源语言」，`public/i18n/locales/en.js` 是全部 key 的权威清单。
- 简体中文是「译文」，放在 `public/i18n/locales/zh-CN.js`。
- 默认语言是英文，与改动前完全一致。
- 语言选择保存在浏览器 `localStorage`，刷新、重开浏览器都会记住。

---

## 1. 文件结构

```
public/i18n/
  index.js              运行时：t() / tp() / setLocale() / applyI18n() …
  cronText.js           把控制 API 返回的英文 cron 描述「重新排版」成中文
  locales/en.js         英文原文（源语言，key 的唯一权威定义）
  locales/zh-CN.js      简体中文译文
tools/
  i18n-check.mjs        翻译自检工具（见第 6 节）
docs/
  i18n.md               本文档
```

前端其余文件（`app.js`、`views/*.js`、`charts.js`、`util.js`、`api.js`、`index.html`）
只引用 **key**，不再出现任何硬编码中文；`server.js`、`lib/*`、`public/themes/*` 完全没有改动。

---

## 2. key 的命名与「稳定」原则

key 形如 `namespace.key`，全小写、点分层级，例如：

| key | 含义 |
| --- | --- |
| `tab.overview` | 顶部标签「总览」 |
| `overview.stat.accountsLabel` | 总览里的统计卡片标题 |
| `accounts.protection.chipTitleOn` | 账号卡片上「连续保护」徽标 |
| `config.group.webhooks` | 配置页分组标题 |
| `ctl.start` | 控制条上的「开始运行」按钮 |

**最重要的一条规则：key 是身份，不是文案。**

- 已翻译的 key **永远不要改名**。改名的代价是译文全部丢失。
- 英文文案本身可以改（改了以后建议顺手核对一下译文），key 不变。
- 需要新文案时**新增 key**，不要复用语义已经变了的旧 key。

这条规则就是「跟随 upstream 更新不用重译」的全部秘密：upstream 改英文措辞时 key 不动，
译文照旧生效；upstream 新增界面文字时，只需要**补一条**新 key 的译文。

值有两种形态：

```js
"runs.chartMetaPlural": "{days} 天共 {points} 积分，{active} 个活跃账号",  // 普通字符串
"logs.buffered": { one: "已缓冲 {count} 条日志", other: "已缓冲 {count} 条日志" }, // 复数形态
```

复数形态由 `tp(key, count)` 使用，根据 `count` 是否为 1 选择 `one` / `other`
（中文两种写法相同，属正常现象；保留 `one`/`other` 是为了让英文和未来的其它语言能正确工作）。

占位符统一写成 `{name}`，由 `t(key, { name: value })` 插值。

## 3. 在代码里怎么用

### 3.1 动态文本 —— 在 JS 里拼字符串时

```js
import { t, tp } from "../i18n/index.js";

t("logs.pause");                                   // 固定文案
t("overview.run.pendingDelay", { seconds: 12 });   // 带参数
tp("runs.chartMetaPlural", active, { points, days, active }); // 带数量
```

### 3.2 静态标记 —— 写在 HTML / 模板字符串里的

```html
<span data-i18n="common.loading">Loading…</span>
<button data-i18n-title="config.reloadTitle" title="…">…</button>
<select data-i18n-aria-label="app.languageLabel" aria-label="Language">…</select>
<input data-i18n-placeholder="logs.filterPlaceholder">
<p data-i18n-html="config.redactedNotice">…</p>
```

- `data-i18n` → 写入 `textContent`
- `data-i18n-html` → 写入 `innerHTML`（**只有**译文本意就含 `<code>` 之类标记时才用）
- `data-i18n-title` / `data-i18n-aria-label` / `data-i18n-placeholder` → 写入对应属性

`applyI18n(document)` 会扫描并填好这些属性；`index.html` 里的标记由 `initI18n()` 处理，
切换语言时 `app.js` 会重新调用一次。

### 3.3 两种上下文，两种标点

`en.js` 顶部的注释写得很清楚：有的值最终进 `innerHTML`（那么 `&amp;`、`&rsquo;` 是字面实体，
应当保留），有的值进 `textContent`（那就要用真实的 Unicode 标点 `—`、`“”`）。
**新增条目时按它实际被消费的方式写**，否则会出现 `&amp;` 直接显示在界面上的问题。

## 4. 回退机制（不会出现 undefined / 空白）

`t()` 的查找顺序是：

```
当前语言  →  英文 en.js  →  直接返回 key 本身
```

因此：

- 某个 key 还没有中文时，界面显示**英文原文**（而不是空白或 `undefined`）。
- 中文译文写成了空字符串时，同样回退英文。
- 代码里写了字典中不存在的 key 时，界面会显示出 key 字符串本身
  —— 这是刻意设计，方便一眼看出漏翻，`tools/i18n-check.mjs` 会把它们列出来。

配置页还有一层**动态回退**：`views/config.js` 里的 `fieldLabel()` / `toggleLabel()` /
`optionLabel()` 会用 `config.field.<路径>.label` 这样的 key 去查字典，
查不到就原样显示代码里自带的英文。这意味着 **upstream 新增一个配置项时，
即使你还没写中文，配置页也照常正常显示（英文），不会崩、不会空**。

## 5. 日期、时间与数字

- `util.js` 里所有 `toLocaleString` / `toLocaleDateString` 的 locale 来自 `dateLocale()`。
- `dateLocale()` 在**英文模式下返回 `null`**，即完全不干预，沿用浏览器默认
  —— 因此英文界面的日期输出与改动前**逐字节一致**。
- 只有切到简体中文时，才把 `zh-CN` 交给 `Intl`，日期随之本地化。
- 数字（`fmtNumber` / `fmtSigned`）刻意**不**跟随语言：纯整数的 `toLocaleString`
  在 en 与 zh-CN 下结果相同，无需改动，也就避免了任何行为差异。
- `util.js` 里的 `tzDateParts()` 使用 `"en-CA"` 是为了拿到 `YYYY-MM-DD` 这种**格式**，
  它跟界面语言无关，**不要**把它改成跟随语言。

## 6. 自检工具：`tools/i18n-check.mjs`

```bash
node tools/i18n-check.mjs            # 人类可读报告
node tools/i18n-check.mjs --json     # 机器可读
node tools/i18n-check.mjs --strict   # 连「无用 key」也当作错误
```

它回答的正是同步 upstream 后最需要知道的两件事：

1. **有没有漏翻？**
   - `ENGLISH FALLBACK` —— 有 key 但缺中文（界面会显示英文，功能正常）
   - `UNKNOWN t() KEY` —— 代码里用了、但 `en.js` 里没有的 key（**必须修**）
2. **占位符有没有对不上？**
   - `PLACEHOLDER MISMATCH` —— 英文有 `{points}` 而中文没有（或反过来），
     会导致界面上直接漏出 `{points}` 字样，或参数丢失（**必须修**）

另外还会报告 `ORPHAN`（只存在于中文、英文没有的 key）、
`EMPTY VALUE`（空译文）、`PLURAL VARIANT MISSING`、`UNUSED KEY`。

退出码在有问题时为 `1`，所以可以直接拿它当 CI / 构建的前置检查。

> `config.toggle.*`、`config.field.*`、`config.option.*`、`config.delay.*` 这几类是
> **运行时拼出来的 key**，工具对它们做了特殊处理，不会被误报成 `UNUSED KEY`。

也可以加到 `package.json`：

```bash
npm run i18n:check
```

## 7. 同步 upstream 新版本的标准流程

```bash
# 1. 用 upstream 的新版本覆盖源码（不要动 public/i18n/ 和 tools/）
#    最关键的一点：public/i18n/locales/zh-CN.js 是「你的资产」，永远保留旧的那一份。

# 2. 跑自检
node tools/i18n-check.mjs

# 3. 按报告处理：
#    - UNKNOWN t() KEY        -> 新 key，在 en.js 与 zh-CN.js 中补上
#    - ENGLISH FALLBACK       -> 补译文即可（补之前界面显示英文，不算故障）
#    - PLACEHOLDER MISMATCH   -> 改译文，让占位符与英文一致
#    - ORPHAN / UNUSED KEY    -> upstream 删掉的旧文案，可以放心清理
#    - EMPTY VALUE            -> 补译文

# 4. 再跑一次，确认干净
node tools/i18n-check.mjs
```

### 为什么不需要重译

| upstream 的改动 | 你需要做的事 |
| --- | --- |
| 改了某条英文文案的措辞 | **什么都不用做**（key 是身份，译文继续生效） |
| 新增了一个界面文案 | 补 **1 条** `zh-CN.js` 条目；在补之前显示英文 |
| 删除了某个功能 | 删掉对应的旧 key（自检会提示 `UNUSED KEY`） |
| 新增了一个配置项 | **什么都不用做**：`config.field.<路径>.label` 查不到就显示代码里的英文；想汉化时再补 key |
| 改了 API、数据结构、调度逻辑 | 与本方案无关，如实合并即可 |

合并时唯一需要人工留意的文件是 `views/config.js`：它用 `t(title)`、`fieldLabel()`、
`optionLabel()` 这类辅助函数去查字典，冲突一般出现在这些调用点上，
解决方式就是「保留你的调用写法，采用 upstream 的数据改动」。

## 8. 新增一种语言（例如繁体中文）

1. 复制 `public/i18n/locales/zh-CN.js` 为 `public/i18n/locales/zh-TW.js`，逐条改译文。
2. 在 `public/i18n/index.js` 的 `LOCALES` 里加一行：

```js
{ id: "zh-TW", label: "繁體中文", dict: zhTW },
```

3. 打开页面，语言下拉框里会自动多出一项；`en.js` 的 key 清单不需要任何改动。

界面上的语言选择框（`#langSelect`）是**从 `LOCALES` 生成的**，不是写死的，
所以新增语言不需要改 `index.html` 或 `app.js`。

如果新语言需要不同的日期格式或 12/24 小时制，再相应调整
`dateLocale()`（`public/i18n/index.js`）与 `cronText.js` 里的 `HOUR24` 集合。

## 9. 术语表（保持全局一致）

| 英文 | 简体中文 |
| --- | --- |
| Dashboard | 仪表盘 |
| Account | 账号 |
| run | 运行 |
| points | 积分 |
| streak | 连续天数 |
| streak protection | 连续保护 |
| punchcard | 打卡任务 |
| daily set | 每日任务 |
| Schedule | 定时任务 |
| scheduler | 调度器 |
| session | 会话 |
| proxy | 代理 |
| Earnable | 可获取 |
| cluster | 簇 |
| webhook | Webhook（不译） |

**刻意不翻译**的内容：

- `Microsoft Rewards`、`ExploreOnBing`、`ntfy`、`Discord`、`Telegram`、`Edge` 等专有名词
- `ACCOUNT_N_*` 之类的账号标识
- `config.json` 的**键名与取值**（`true` / `false` / `whitelist` / 正则表达式等）
- 日志正文里出现的英文关键词（那是脚本输出的原文，不属于界面文案）
- 主题名称（由服务端从 `public/themes/*Theme.ts` 生成）
- cron 表达式本身

另外，`schedule.js` 的「运行时间」描述来自控制 API 返回的**英文句子**。
`public/i18n/cronText.js` 只对它做**重新排版**（`Every 30 minutes` → `每 30 分钟`、
`9:00 AM` → `09:00`），不重新解析 cron、不碰 `lib/cron.js`。
遇到无法识别的句式时直接原样返回英文 —— 宁可显示英文，也不会显示错的东西。

## 10. 已知事项

- **`public/sw.js`（PWA Service Worker）**：项目里存在这个文件，但全项目**没有任何地方
  注册它**（`navigator.serviceWorker.register` 不存在），所以它当前不会生效。
  如果将来 upstream 启用了它，需要把 `/i18n/index.js`、`/i18n/locales/*.js` 加入它的
  `ASSETS` 列表，并提升 `CACHE_NAME` 版本号，否则浏览器可能继续用旧缓存的界面。
  本次改动**没有**动这个文件，以免影响上游合并。
- **首次绘制**：`index.html` 里的静态文字在 `app.js` 执行前是英文。模块脚本在
  DOM 解析完成后、首次渲染前执行，因此实际看到的是「直接就绪」的效果；
  极端慢的设备上可能出现一次极短的英文闪现，这属于可接受范围。
- **`<html lang>`**：`index.html` 里写的是 `lang="en"`，页面加载后由 `initI18n()`
  改成当前语言，以保证浏览器字体、断词、拼写检查跟随语言。
